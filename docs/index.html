Analytical Questions

Q1. Can we predict trip duration (minutes) from distance, pickup time, and zone?

Q2. How do demand and duration vary across NYC — where are the hotspots, and how does rush hour affect travel time?

Spark Components Used
✓ Structured APIs — typed ingestion, cleaning, joins, feature engineering
✓ Spark SQL — demand hotspots, hourly aggregations
✓ Structured Streaming — 12-batch micro-feed simulation
✓ MLlib — Random Forest + Linear Regression regression pipeline
Key Finding

Rush-hour status and pickup hour together account for ~21% of the model's predictive power — even though average trip distance barely changes across the day (~2.9 mi all day), average duration nearly doubles during congested windows (7–10 AM: ~18.7 min, 4–7 PM: ~21 min) vs. overnight (~10 min). A dispatcher predicting ETAs from distance alone would be systematically optimistic during rush hour.

Pipeline Architecture

Click any stage to see implementation details. Run with bash run.sh or make run.

0
generate_sample.py
Seed-reproducible synthetic dataset generation
DATA
Generates 40,000 trip rows × 13 columns using numpy with seed=42. Embeds a deterministic rush-hour signal (duration × 1.9 for 7–10, × 2.1 for 16–19) and ~2% dirty rows (zero distance, negative fare) so the cleaning stage is meaningful.

Output: data/sample/yellow_tripdata_sample.csv and data/sample/taxi_zone_lookup.csv (35 zones).
1
ingestion.py — Structured APIs
Typed schema → CSV/Parquet ingestion → curated Parquet write
STRUCTURED API
Reads the trip CSV with an explicit StructType (no inference — safer and faster at scale). Supports real TLC Parquet files via normalize_trips() which projects drifting real-file schemas onto the 13 canonical columns.

Runs a data-quality profile: row count, null counts, zero/negative distance, negative fare.

Output: data/curated/trips/ (Parquet) — downstream stages avoid re-parsing CSV.
2
transformations.py — Structured APIs + Spark SQL
Clean → feature engineering → broadcast join → SQL aggregations
SQL
Cleaning: removes zero-distance, negative-fare, >3hr, zero-passenger rows. Computes trip_duration_min target.
Feature engineering: pickup_hour, pickup_dow, is_weekend, is_rush_hour, avg_speed_mph.
Broadcast join: attaches borough/zone from the 35-row lookup (no shuffle).
Spark SQL: registers temp view and queries demand-by-hour + top-10 pickup zones.

Output: data/curated/features/ (Parquet) + data/outputs/demand_by_hour/ + data/outputs/top_pickup_zones/.
3
streaming.py — Spark Structured Streaming
12-file micro-batch simulation → stateful aggregation → sink
STREAMING
Splits the trip data into 12 small CSV files in data/stream_source/ to simulate an arriving feed.

Streaming reader: maxFilesPerTrigger=1 — processes one file per trigger.
Aggregation: running trips + avg_fare + avg_duration per pickup hour, outputMode("complete").
trigger(availableNow=True) processes all micro-batches then terminates cleanly.

The aggregation function is factored into aggregate_zone_stream() — a pure transformation testable on static DataFrames.
4
ml_pipeline.py — MLlib Regression
StringIndexer + OHE + VectorAssembler → RandomForest / LinearRegression
MLLIB
ML Pipeline stages: StringIndexer → OneHotEncoder on pu_borough + payment_type → VectorAssembler (6 numeric + 2 encoded) → regressor.

Models: RandomForest (40 trees, depth 8, seed=42) as primary; LinearRegression as baseline.
80/20 split (seed=42); evaluated with RMSE, MAE, R².

RF RMSE: 3.87 min · MAE: 2.63 min · R²: 0.867
5
eda.py — Spark SQL + Visualizations
Summary stats, SQL queries, 5 charts saved to docs/figures/
EDA
Computes summary statistics, runs 4 Spark SQL queries (hourly demand, borough breakdown, payment type, top zones), and produces 5 matplotlib charts saved to docs/figures/:

How the model works
The Spark ML Pipeline uses RandomForestRegressor (40 trees, depth 8) trained on 31,369 trips. Features: trip_distance (importance 78%), is_rush_hour (16%), pickup_hour (5%), plus categorical borough/payment encoding.

This interactive widget simulates the model formula: base_speed × congestion_multiplier derived from the training patterns.
